# F4 design for v0.2

Status: implemented in 0.2.0.

This document records the F4 engine in `src/compute/f4`. It is not a proof of
correctness. `KNOWN_ISSUES.md` states the evidence and its limits.

## 1. Scope

Version 0.2 adds one prime-field backend:

\[
\text{critical pairs}
\to \text{symbolic preprocessing}
\to \text{sparse matrix}
\to \text{finite-field elimination}
\to \text{new basis elements}.
\]

The engine computes over \(\mathbb F_p\), where
\(2\le p\le 2^{31}-1\). It uses the sealed `grevlex-v1` order. It accepts at
most 256 variables. One exponent is at most 65,535.

The release also retains classic F5. F4 is the default. Classic remains the
independent engine oracle and the v1 certificate producer.

This release does not add rational arithmetic, runtime monomial orders,
user-defined pair criteria, or new coefficient domains.

## 2. Public contract

`ComputeOptions::backend` selects `Backend::F4` or `Backend::Classic`.
`ComputeOptions::threads` controls only uncertified F4:

- zero uses Rayon's global pool;
- one uses the calling thread;
- a larger value creates a pool for that run.

Classic and certified runs use one thread. Thread count changes neither the
basis nor the certificate bytes.

`Ideal::groebner_basis_with_report` returns `ComputeReport`. An F4 report
contains `F4Counters`: batch, matrix, pivot, lane, table, and pair counts.
Counters observe a run. They do not control it.

The engine returns a monic reduced basis sorted strictly by descending leading
monomial. It reports partiality through `ComputeError`:

- `Timeout` and `MemoryLimitExceeded` report exhausted budgets;
- `ExponentLimit` reports an F4 exponent above 65,535;
- `TableFull` reports a monomial table with no remaining `u32` identifier.

No condition truncates a basis or matrix silently.

## 3. Monomial representation

### 3.1 Interning

`MonomialTable<L>` hash-conses exponent vectors. A `MonomialId` is a table-local
`u32` index. ID zero is the identity monomial. The table is append-only during
one use, so an ID remains stable.

An ID has no `Ord` implementation. Numeric ID order is unrelated to grevlex.
All comparison uses `MonomialTable::cmp`.

Each table stores:

- packed exponent words;
- total degree;
- a divisibility mask;
- a deterministic hash;
- a hash index from content to ID.

The fixed hash seed makes one insertion sequence deterministic. Correctness
does not depend on hash iteration order.

### 3.2 Lane widths

Exponent vectors use guarded lanes in `u64` words:

| Packing | Lanes per word | Largest exponent |
| --- | ---: | ---: |
| `Lanes8` | 8 | 127 |
| `Lanes16` | 4 | 32,767 |
| `Lanes32` | 2 | 65,535 |

The run starts at the narrowest width that holds the input. If an intermediate
monomial exceeds that width, the run discards its state and restarts at the
next width. At most two restarts occur. Overflow at `Lanes32` returns
`ExponentLimit`.

The reserved high bit in each lane makes componentwise subtraction and
divisibility tests exact. No lane arithmetic may set that bit.

### 3.3 Divisibility masks

Each monomial carries a 32-bit mask. A set bit means one exponent crossed a
fixed threshold. If the mask of \(a\) has a bit absent from the mask of \(b\),
then \(a\nmid b\). A passing mask test is only a candidate; packed exponent
comparison decides divisibility.

The threshold ladder is fixed when a table is created. It depends only on the
variable count and the largest input exponent.

### 3.4 Table boundaries

The basis, pair-update workspace, and symbolic batch use distinct tables.
Functions that cross a boundary copy exponent content and intern it in the
destination table. An ID never crosses by value.

## 4. Basis state

`Basis` owns the long-lived monomial table and polynomial storage. A polynomial
stores parallel monomial and coefficient slices. Coefficients are reduced
modulo \(p\). A live basis element is monic.

The lead index groups leading monomials by degree and divisibility mask. A
lookup returns a divisor, preferring a shorter reducer where the choice is
otherwise valid.

Inserting a new leading monomial retires any live elements it makes redundant.
Retired elements remain addressable until no queued pair or trace can refer to
them. Two live elements never share a leading monomial.

If a nonzero constant enters the basis, the result is immediately `{1}`.

## 5. Pair management

`PairSet` stores critical pairs and their least common multiples. Updating the
set applies the product criterion and Gebauer-Möller criteria B, M, and F.

The coverage invariant holds: every pair deleted by a criterion remains
covered by a retained pair or a product relation. Tests compare the update
against an independent closure calculation.

The next batch contains the least available least-common-multiple degree.
Within a degree, sorting uses grevlex and then stable basis indices. An internal
batch cap may defer the suffix without changing its order.

## 6. Symbolic preprocessing

For each selected least common multiple, preprocessing adds the endpoint
multiples. It then closes the union of their supports under available basis
reducers.

Each encountered monomial becomes one matrix column. A reducible column gets
one upper reducer row. A non-reducible column is free. Columns descend in
grevlex. Row supports ascend by column index.

The default strategy chooses the smallest source index for equal leading
columns. The strategy is not part of the public API.

The same closure builds the final interreduction matrix. Each live basis
element starts as the reducer row of its own leading column.

## 7. Sparse matrix

`Batch` separates upper reducer rows from lower rows. Rows store sparse column
indices and coefficients. Basis-backed rows borrow coefficient storage. New
rows use batch-owned arenas.

The matrix builder checks these invariants in debug builds:

- columns descend in grevlex;
- each row support strictly ascends;
- each pivot column names exactly one reducer row;
- reducer rows are monic;
- every column index is in range.

The builder reuses allocations between batches. No row owns a monomial vector.

## 8. Field kernel

`Small31` implements arithmetic for \(p<2^{31}\). Coefficients are `u32`.
Dense accumulators are `u64`.

Pivot application uses Shoup multiplication. A precomputed quotient gives the
high half of one product without division. The kernel periodically reduces the
accumulator so every lane remains within the proven `u64` bound.

Unit tests compare this arithmetic with direct `u128` products. Random sparse
matrices compare with an independent dense elimination at small primes and at
the benchmark modulus.

## 9. Elimination

The kernel reduces lower rows against the upper pivot block. New leading
columns install new pivots. Zero rows disappear. Surviving pivots are sorted by
their leading columns before insertion.

For an uncertified run, a batch may reduce independent lower rows in parallel
when its work estimate reaches the internal threshold. Each worker owns its
accumulator. The caller's memory limit charges those accumulators before
allocation.

Trace recording disables parallel reduction. A certificate records a fixed
operation sequence, so certified execution stays serial.

Final interreduction uses the same matrix and field kernel. It reduces every
tail, normalizes pivots, and converts the result to public `Polynomial` values.

## 10. Main loop

For one lane width, the engine performs:

1. Normalize and intern the input.
2. Seed the basis and pair set.
3. Select the lowest-degree pair batch.
4. Run symbolic preprocessing.
5. Build and reduce the sparse matrix.
6. Insert new pivots and update pairs.
7. Repeat until the pair set is empty or the basis is `{1}`.
8. Interreduce and sort the live basis.

Every accepted nonunit pivot has a leading monomial outside the current
leading-monomial ideal. Thus insertion gives a strict ascending chain of
monomial ideals. The ascending chain condition proves finite insertion.
`KNOWN_ISSUES.md` gives the termination argument and separates it from
correctness.

## 11. Limits

The deadline is computed once at call entry. Long loops poll it at fixed
strides. Batch boundaries poll it immediately.

The memory estimate includes:

- basis polynomials and their monomial table;
- the pair set and pair-update table;
- symbolic and matrix tables;
- row arenas and reduction workspaces;
- parallel worker accumulators;
- trace storage during certification.

The engine checks projected allocations before growth where practical. If a
batch exceeds the limit, the engine requeues its second half, releases the
failed batch capacity, and retries. A one-pair batch that still exceeds the
limit returns `MemoryLimitExceeded`.

The estimate counts owned capacities. It is not a process RSS limit.

## 12. Determinism

The following choices have total tie-breaks:

- pair order;
- symbolic source order;
- monomial insertion order;
- column order;
- pivot installation order;
- returned basis order.

Parallel workers write one result slot per input row. The calling thread joins
and installs those slots in row order. Hash tables serve only content lookup.
Their iteration order never enters output order.

Tests compare repeated runs and thread counts. Certified runs also compare
certificate bytes.

## 13. Certification

F4 writes `sylv-gb-cert-v2`. The trace contains batch rows, elimination steps,
basis insertion, final interreduction, membership divisions, and pair
witnesses. `docs/certificate-v2.md` is the frozen contract.

The v2 verifier is code-isolated from the engine. It replays the trace with its
own decoder, arithmetic, polynomial type, monomial type, and order. Acceptance
establishes both ideal inclusions, Buchberger's criterion, and reduced canonical
form.

Classic certification remains `sylv-gb-cert-v1`. No certificate schema covers
the rationals.

## 14. Validation

The release gates include:

- unit tests for monomials, fields, pair criteria, matrices, and elimination;
- deterministic differential tests against a criterion-free Buchberger oracle;
- complete-basis comparisons between F4 and classic;
- fixed counterexamples in every generator order;
- malformed, truncated, and byte-mutated certificate tests;
- an ignored exhaustive \(\mathbb F_2\) sweep;
- an ignored degree-reversal sweep;
- an ignored `eco-8` comparison between F4 and classic.

The external gate runs `cyclic-7`, `katsura-9`, `eco-9`, and `noon-6` over
\(\mathbb F_{1073741827}\), grevlex, one thread, a 16 GiB memory limit, and a
120 s time limit. It requires geometric-mean F4 time at most 5 times msolve and
worst-case time at most 10 times msolve.

Those ratios are release thresholds, not measurements. The current measured
record is `benchmarks/gb-comparison/REPORT.md`.

## 15. Non-goals

Version 0.2 does not claim:

- a proof of engine or verifier correctness;
- equality between the memory estimate and process RSS;
- performance outside the recorded benchmark;
- stable pre-1.0 API compatibility;
- rational coefficients or rational certificates;
- configurable monomial orders;
- GPU or distributed execution.
